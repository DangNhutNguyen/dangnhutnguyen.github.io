# Focumia: I Built a Productivity App Because I Wasn’t Productive

*Logbook 07 · 2025*

I once had a very complete productivity system. It had tasks, calendars, goals, notes, documents, and several colors chosen with surprising seriousness. There was only one problem: I spent more time repairing the system than doing the work inside it. It was procrastination with excellent organization. In 2025, I began Focumia, a productivity application built from a real need of my own. I was studying several areas, building several projects, and regularly feeling that everything lived in a different place. I wanted a space closer to the way I thought instead of continuing to patch tools that already existed. The source code is available on [GitHub](https://github.com/DangNhutNguyen/Focumia). The Internet is not short of to-do applications. I knew that. When a developer says, “The existing tools do not match my workflow,” there is perhaps a fifty-percent chance that a real pain point exists and a fifty-percent chance that the developer simply wants to design a sidebar. I had both. My problem was not only forgetting tasks. I wanted to see the relationship between what I did today and a longer learning goal. A calculus lesson, a DSA practice session, a neural-network experiment, and a research draft do not become complete in the same way. If all of them are only checkboxes, the system becomes very clean and tells me very little.

I wanted Focumia to answer: what must be done now? which project does this work serve? which goal am I learning for? if I return after several days, what is the next step? That was the product question. The engineering began objecting almost immediately. On the interface, I can name something a task, session, goal, or milestone. In code, each name needs a clear behavior and relationship. Can one task belong to several projects? Can a completed study session be edited? If the goal changes, should the old progress remain? Is a note an attribute of a task or an independent object? These questions are less exciting than choosing a font. They determine whether the application survives its second month of real use. Focumia taught me that software design does not begin with the number of features. It begins with modeling the world those features claim to represent. If the model is wrong, a beautiful interface only helps the user reach the wrong place faster. The advantage of building an application for myself is having a user who is always available to test it. The disadvantage is that this user knows exactly which shortcuts I faked and which screens look good only in a demonstration.

When I used Focumia in daily life, I found problems that did not appear in the design: if entering a task requires too many steps, I will not enter it; a dashboard with too much information eventually becomes wallpaper; a feature that requires willpower to maintain will soon have no data; more notifications do not make me disciplined; they make me better at swiping notifications away; learning does not progress evenly, so a progress bar can create false precision. This is the part of product development I enjoy. The user-even when the user is me-does not obey the diagram. Technically, many task-management applications can be described through create, read, update, and delete. A productivity product rarely fails because it is missing a Delete button. It fails when the cost of updating the system exceeds the value returned to the user. It fails when it requires an ideal version of the user-always consistent, always able to prioritize, always remembering to log the day. I once designed for “tomorrow’s Nhựt,” the person who wakes on time, follows the schedule, and completes every field. The person actually using the application was Nhựt at eleven at night, tired after studying, wanting to write only one sentence so that tomorrow would not begin from nothing. Those two people need different products.

I would begin with fewer questions: which action does the user perform every day? what is the minimum information that makes the next return easier? if the user leaves for a week, how does the system help them return? I would also release a small version earlier instead of waiting for the architecture to represent an entire life. An extensible system does not need to know everything in advance. It needs a core that is correct enough and real data that shows where to expand. Most importantly, I would separate two goals: learning engineering and building a product. An interesting engineering choice may be poor for the user. A simple product solution may not let me test the technology I want to learn. If I do not say which goal I am optimizing, the project becomes trapped between both. Focumia has not solved the management of my life. Honestly, I do not think any application can. But the project changed the way I look at educational technology and productivity. A good tool does not do the hardest part-sitting down and learning. It only reduces the number of times the learner has to rediscover the direction. That goal is smaller than “optimizing life.” It is also much more useful. I still enjoy designing sidebars. Now, at least, I know the sidebar is not the core feature.
