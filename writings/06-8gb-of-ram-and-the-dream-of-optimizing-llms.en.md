# 8GB of RAM, a Radeon VII, and the Dream of Optimizing LLMs

*Logbook 06 · From 2024 to 2026*

The laptop I use every day has 8GB of RAM. This is not a particularly romantic fact when my long-term goal is to research large language models. Even the name “large language model” sounds like a reminder that my hardware was not invited to the party. For heavier experiments, I can use a T4 on Google Colab or a Radeon VII with 16GB of VRAM, hardware closely related to the MI50. They are useful. They still do not turn my room into a data center. Whenever I choose a model, batch size, or method for loading weights, the memory question often arrives before the accuracy question. At first, I treated that as a disadvantage I needed to work around. Later I began to wonder: perhaps this is the research question I actually want to pursue. On the Internet, the sentence “run this model on consumer hardware” may mean: the weights load, but every token takes a very long time; inference works, but fine-tuning does not; it runs through quantization, offloading, or loading only part of the model at a time; it runs in a reduced configuration, not the original one; it runs once-long enough to take a screenshot. None of these is automatically meaningless. The problem begins when the condition is left unstated and I mistake a proof of concept for a usable system.

While experimenting with AirLLM and Kimi-K3 on Colab, the most valuable lesson was not the feeling that “a very large model ran.” It was seeing the boundary among loading the model, inference speed, storage capacity, and practical use. A technique may reduce VRAM by moving layers into memory only when they are needed. That does not make the parameters disappear. The cost simply moves somewhere else: system RAM, disk space, data-transfer bandwidth, or waiting time. There is no free lunch. There is only a bill moved into another column. My old reaction to an out-of-memory error was to reduce the batch size. It often worked, but it did not answer the more important question: where was the memory being used? An AI experiment may need memory for: model weights; saved activations; gradients; optimizer states; batch data and padding; temporary memory used by the framework or kernels. Inference and training are therefore two very different worlds. A model that barely fits for inference in 16GB of VRAM may be nowhere near trainable. Gradients and optimizer states alone can rewrite the entire memory budget. Once I was forced to count, I began to understand architecture in a different way. Every choice-context length, precision, batch size, layer count, hidden dimension-leaves a physical trace on the hardware. The model may look abstract in a paper. It still has to live somewhere.

There are many techniques for making models more accessible: mixed precision, quantization, parameter-efficient fine-tuning, gradient checkpointing, distillation, sparsity, and offloading. The list can quickly become a collection of fashionable terms. I want to learn them through questions instead: which part of the cost does this technique reduce? what does it trade away-accuracy, speed, or stability? does the benefit remain on different hardware? does the result come from the algorithm or a better implementation? was the baseline measured under the same conditions? This is also where physics and experimental thinking return. A good number means little if I changed three variables at once. A smaller model is not necessarily more efficient if latency rises sharply. A method that “saves” GPU memory may simply push the burden onto the CPU and I/O. Optimization is not the act of making one number smaller. It is deciding what I am willing to pay with. I am trying to follow a simpler process: begin with a model small enough to run many times; establish a reproducible baseline; profile time and memory before optimizing; change only one group of factors in each experiment; save configurations, seeds, library versions, and failed results; use an expensive run only to test a hypothesis that has already been narrowed down. This sounds slower. It is often faster than burning an entire Colab session on one run and discovering that I cannot say what the run demonstrated.

Limited resources also force me to care about the quality of the question. If I can run only five experiments, I cannot spend the first four discovering what the project was supposed to ask. Compute still matters. Some questions cannot be answered seriously with one 16GB GPU. A lack of hardware should not become a moral story in which a sufficiently talented person no longer needs resources. But I also do not want to wait for a cluster before beginning to research. Many questions about efficiency can be studied through smaller models, smaller benchmarks, and careful measurement. If an idea has value only when I can afford to run it, I would rather learn that early. My goal is not to prove that 8GB of RAM is enough for everything. My goal is that, when I eventually have more resources, I will not use them to hide a poorly designed experiment. The 8GB laptop can be painfully slow. Still, it taught me one question rather quickly: **What does the next byte of memory actually buy?**
