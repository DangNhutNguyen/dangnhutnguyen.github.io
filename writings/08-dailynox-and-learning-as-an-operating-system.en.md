# Dailynox and the Attempt to Turn Learning into an Operating System

*Logbook 08 · 2025*

After building one productivity application, the reasonable response would probably have been to rest. My response was to imagine a larger system. Dailynox began as a learning platform and a LifeOS: a planner-like space that could work in Vietnamese and English, adapt to different screen sizes, and offer a dark mode so that I could feel slightly more serious while studying at night. The interface was only the surface. The question that kept the project alive was this: **if learning has a structure, how should software represent that structure?** Suppose I want to study AI. “Learn Python,” “study linear algebra,” “build MNIST,” and “read about transformers” can all sit in the same to-do list. On the screen, they look like four equal tasks. In reality, they have different dependencies, levels, and outcomes. A module contains subjects. A subject contains theory, exercises, projects, and assessments. One concept may appear in several places. A project may require knowledge from several branches. Some material has been “seen” but cannot yet be used. Some material was understood and then forgotten months later. I wanted Dailynox to represent a learning tree: **Roadmap → Module → Subject → Topic → Lesson → Theory / Exercise / Project.** The moment I put this structure into the data model, the tree began to resist.

Knowledge in real life is not always a tree. A graph may be more accurate because one lesson can depend on several others. But graphs are difficult to display, difficult to edit, and very good at becoming a beautiful picture that leaves the learner with no idea what to study today. It is a familiar trade-off: the closer the model moves toward reality, the more the interface risks becoming unusable. I like the phrase “an operating system for life,” but it gives a project permission to grow without end. If it is a LifeOS, why not add personal finance? A habit tracker? Calendar? Journal? Knowledge graph? AI assistant? Document sync? One brainstorming session can produce a backlog suitable for a company, while the current team is still myself and several browser windows. Feature creep rarely begins with a bad idea. It begins with many good ideas that do not serve the same core action. For Dailynox, I wanted to preserve one action: The learner opens the system, understands where they are, completes one concrete step, and leaves enough context to continue next time. Any feature that does not improve one of those four moments has to wait. At least, that is the theory. In practice, I still sometimes want to add a dashboard simply because the chart would look nice. One of the hardest problems is modeling progress.

If I finish a video, have I completed the lesson? If I solve three of ten exercises, am I thirty percent finished-or more? If a project fails but teaches me the problem deeply, does it count as progress? Software prefers clear states: not started, in progress, complete. Learning contains less comfortable states: I think I understand; I understand when I see the solution; I can do it with a hint; I can do it alone; then I forget. I do not want Dailynox to reward only the Complete button. The system should preserve evidence of capability: notes I extracted; exercises I can solve independently; the most recent review; projects where the concept was applied; questions that remain open. A percentage can help with direction. It becomes dangerous when it pretends understanding can be measured to the nearest integer. I want the interface in both Vietnamese and English because that is how I learn. I often meet a concept through English material, then need a language closer to my own thinking in order to explain it. Some technical terms translate naturally into Vietnamese. Others become difficult to recognize when I meet them again in documentation. A bilingual learning platform should do more than replace the text on a button. It should let a learner keep both names, search in both languages, and move between them without treating one language as the secondary version.

This sounds like a small product detail. It directly affects access to knowledge. Many people beginning in technology have to learn the subject and the language used to describe the subject at the same time. Dailynox taught me that a data model is a statement about how I see learning. If everything is a task, I am saying that learning is the completion of work. If everything is a note, I am saying that learning is the collection of information. If I have only courses and lessons, I am assuming that everyone follows a straight line. No model is entirely correct. The designer’s job is not to discover the perfect ontology for all human knowledge. It is to choose a model useful enough for the people and behavior the product serves. If I began again, I would interview “Nhựt during his busiest week” before “Nhựt on his most motivated day.” I would prototype the return after an interruption, because that is more real than finishing on schedule. And I would keep the graph behind the interface, revealing it only when it helps choose the next step. I still like the name LifeOS, with one condition. A good operating system manages resources and helps programs run. It does not decide how the user must live. A learning platform should do the same: make state clearer, reduce friction, and preserve context without turning life into a sequence of progress bars.

Dailynox remains a project in development, not a complete answer. But it has given me one question worth keeping: How can software respect learning as a messy process while still helping the learner find the next step? If I answer that, perhaps I still will not have built an operating system for life. But I may have built a place where a lesson is not lost halfway through.
